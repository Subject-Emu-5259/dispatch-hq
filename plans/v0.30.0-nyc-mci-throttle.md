# v0.30.0 — New York City, Mass-Casualty Chain & Throttle Observability

> **Theme:** Close the last "declared-but-unfinished" launch-city gap (NYC is on
> the ladder and in the picker but has no precise boundary or trauma center),
> add a distinct mass-casualty chain that matches the scale of a mega-city, and
> make the 429 throttles observable so a spam wave or a misbehaving client is
> visible from the Admin console instead of a silent error-rate.

**Current state:** v0.29.4 live (mobile/tablet navigation overhaul, CAD console
rebuild, unit-panel rescue, sidebar-default fix). The per-account write-route
throttles from v0.27 are tuned but **unobservable** — nothing records how often
they fire or who they hit. This batch is one data slice (NYC, mirroring the
Little Rock v0.24 pattern), one content slice (a new EMS chain), and one
server+UI slice (429 counters + admin surface). No schema changes → **no
`--db-push`**.

---

## What already exists (do NOT re-implement)

- **NYC is already on the ladder at L6** (`cityProgression.ts`) with a picker
  card (`CitySelectionScreen.tsx`) and a station-spot config (`gameSetup.ts`
  `'new-york'`). What it **lacks** vs. the other four launch cities: a precise
  city-limits boundary polygon and a regional trauma-center referral — so
  missions spawn on a generic bbox and hospital overflow falls back to the
  generic "Regional Trauma Center".
- **`ems_chain` already exists** ("Mass Casualty Response": multi_victim →
  cardiac_emergency → traffic_stop). The new chain must be **distinct** from
  it — not a re-label of the same stage list.
- **Chain spawning is live** — `spawnChainStage` (`apps/web/src/lib/missionChains.ts`)
  fires on mission completion (`App.tsx` ~line 2031), rewards stages past 1 at
  ×1.25 (`chainBonusForStage`). New chains need zero wiring, just a
  `CHAIN_DEFINITIONS` entry + templates.
- **Rate limiter is in-memory token buckets** (`servers/game-server/src/lib/rateLimit.ts`),
  keyed per-IP or per-player, with a 10-min sweep. It returns 429 + `Retry-After`
  but **records nothing**.
- **Admin console exists** (`routes/admin.ts`, mounted behind
  `app.use('/api/admin/*', authMiddleware)`) with an `/overview` route — the
  natural home for a throttle readout.

## Tasks

### 1. Fifth launch city: New York City (precise boundary + referral)

**Files:** new `apps/web/src/data/newYorkBoundary.ts`, `apps/web/src/data/cityBoundaries.ts`,
`apps/web/src/lib/hospital.ts`, `scripts/prewarm-map.sh`, `apps/web/src/lib/hospital.test.ts`,
`apps/web/src/lib/cityProgression.test.ts`

Mirrors the Little Rock slice (v0.24.0 §Slice 1) for NYC:

- **1.1** New `newYorkBoundary.ts` — OSM relation for New York City
  (relation 175905, admin_level 8, five-borough consolidated boundary) →
  `CityBoundary` format (`{ name: 'New York City', bounds, rings }`),
  Douglas–Peucker to a few hundred points. Verify: Manhattan/Long Island City
  inside, Jersey City (west bank) and Newark excluded.
- **1.2** Register in `NORMALIZED_BOUNDARIES` — `new-york-city`,
  `new-york`, `new-york-us` keys (same flexible-key pattern as Little Rock).
- **1.3** Trauma referral — add `'new york': 'Bellevue Hospital Center'` to
  `REGIONAL_TRAUMA_CENTERS` (Bellevue is NYC's real Level-1/regional referral).
  Fallback behavior for player-typed city names is untouched.
- **1.4** Ops + tests — add NYC's bbox to `scripts/prewarm-map.sh` (same
  treatment Little Rock got); assert `cityUnlockLevel('New York City') === 6`
  (already true — pin it), `traumaCenterFor('New York City') === 'Bellevue
  Hospital Center'`, and that `getCityBoundary('New York City')` returns the
  precise ring (not undefined).

**AC:** NYC missions spawn inside the five-borough polygon; overflow diverts to
Bellevue; the picker/ladder are unchanged (already shipped in v0.24).

**Feasibility:** High. Pure data + registry + one constant + tests — the exact
shape of the Little Rock slice, which shipped cleanly in v0.24. The only real
work is sourcing/cleaning the polygon (use the same TIGER/OSM pipeline as
Little Rock; a 200–300 point Douglas–Peucker ring is plenty at map zoom).

### 2. EMS mass-casualty chain: "Mass Transit Incident"

**Files:** `packages/shared/src/constants/missions.ts`,
`packages/shared/src/constants/chainMissions.test.ts`

New chain, deliberately distinct from the existing `ems_chain` (which is
multi_victim → cardiac → traffic stop):

```
mci_chain — "Mass Transit Incident"
  bus_crash (new template, ems)      → multi_victim (ems)      → hazmat_medical (ems)
```

- **2.1** New `bus_crash` template — category `ems`, difficulty ~7–8, requires
  2× ambulance + 1× paramedic (with minTrainingLevel 1), `poiTypes: ['road',
  'intersection', 'public']`, icon `🚌`. **Credits/XP must land inside the
  per-service band** (the v0.27 band audit — check `rewardBandFor` before
  committing numbers; aim mid-band: ~900 cr / ~150 xp at D7, then run the band
  tests).
- **2.2** Add `mci_chain` to `CHAIN_DEFINITIONS` with the three stages above.
  All follow-ups reuse **existing** templates (`multi_victim`, `hazmat_medical`),
  so nothing else in the economy shifts.
- **2.3** Tests — pin the stage sequence/services (bus_crash is EMS, follow-ups
  stay EMS, honoring the "EMS chain" identity), `nextStage` termination at
  stage 3, and unknown-id → null. Mirror `chainMissions.test.ts`'s existing
  `chemical_chain` case.

**AC:** Completing a bus crash spawns a Mass Casualty Incident, then a Hazmat
Exposure at the same location, each ×1.25 rewarded, all through the existing
`spawnChainStage` path.

**Feasibility:** High. One new template + a 3-line chain definition + tests.
The one trap is band-safety: the v0.27 XP banding means `bus_crash` must be
tuned inside its difficulty band or the shared band audit fails — budget a
tuning iteration.

### 3. 429-throttle observability counters (server)

**Files:** `servers/game-server/src/lib/rateLimit.ts` (+ `rateLimit.test.ts`),
`servers/game-server/src/routes/admin.ts`, `serve-combined.ts`, `index.ts`

The limiter currently fires silently. Add an in-memory counters sidecar:

- **3.1** `RateLimitStats` — per-route-label counters
  (`{ route: 'auth/register' | 'player/stats' | …, allowed, blocked, lastBlockedAt }`)
  plus a bounded per-key offender list (top N by blocked count, IP or player
  id, with `Retry-After` when last blocked). Keep it a simple `Map` alongside
  `buckets`; the existing 10-min sweep also prunes dead stat entries. `label`
  is a new optional `RateLimitOptions` field (defaults to the route path) so
  the route table can name itself without string surgery.
- **3.2** `GET /api/admin/rate-limit` — admin-protected, returns the snapshot
  (`{ routes: […], offenders: […], since: ISO }`), zero side effects. Mounted
  in `adminRoutes`; both `serve-combined.ts` (prod) and `index.ts` (dev) get it
  via the shared route module — no route-table divergence.
- **3.3** Tests — extend `rateLimit.test.ts`: counters increment on allowed vs
  blocked, per-key offenders rank correctly, sweep clears dead entries, and the
  admin route requires auth (401 without, 200 with) and reports a blocked
  request.

**AC:** After a 429 wave, `GET /api/admin/rate-limit` shows which route and
which key were hit, without a single log line change.

**Feasibility:** High. ~60 lines in the limiter + one admin route + tests. The
counters are in-memory like the buckets — documented as per-instance
(consistent with the existing limiter's own caveat). No schema, no Redis.

### 4. Admin console: throttle readout row

**Files:** `apps/web/src/components/AdminPanel.tsx` (or the admin overview
component it renders), `apps/web/src/lib/apiClient.ts` (one typed fetch)

analytics row:

- **4.1** Fetch `GET /api/admin/rate-limit` on the overview (guarded — a 401/404

  total blocked (this window), top offenders (up to 5, key + blocked count +

  Threshold-highlight rows where `blocked / allowed > 5%`.
- **4.2** Follow the existing admin panel conventions (dark Tailwind cards,
  `tabular-nums`, same refresh cadence as the analytics row — auto-refresh or a
  manual refresh button consistent with what the panel already does).

**AC:** The commander sees at a glance whether a throttle is working or being
hammered, and which account/IP is the source — no server logs needed.

**Feasibility:** Medium-High. Straightforward fetch + cards; the only
uncertainty is which component renders the overview (confirm whether the admin
panel fetches `/overview` or `/analytics` and reuse that pattern). No
game-state coupling.

## Risks / notes

- **Band-safety is the one real risk** (Task 2): `bus_crash` credits/XP must
  pass the v0.27 per-service band audit. Mitigation: tune from an existing
  in-band D7 template (`fall_rescue` is a good anchor) and run the band tests
  before the chain test.
- **NYC polygon size:** the five-borough boundary is large; keep the
  Douglas–Peucker tolerance such that Staten Island's shoreline stays
  recognizable but the ring stays < 400 points. Prewarm covers the bbox so
  tiles exist before the first player picks NYC.
- **Counters are in-memory** (same caveat as the buckets): they reset on
  restart and are per-instance. Fine for the single-instance deployment;
  noted in the doc so a future multi-instance move knows to relocate them.
- **No `--db-push`** — nothing in this batch touches `schema.ts`.
